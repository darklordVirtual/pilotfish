# Peacetime evolution, frozen survival runtime

Status: V2 architectural target.

Pilotfish separates **system improvement** from **operational adaptation**.

The system may improve aggressively while it is in a controlled engineering environment. The deployed SURVIVAL runtime does not learn, rewrite itself, or depend on generative inference. It adapts its decisions to the world while executing a previously verified implementation and authority envelope.

## 1. Core rule

> Pilotfish MAY adapt its decisions during SURVIVAL, but MUST NOT adapt the rules that define the permitted decision space.

That distinction is deliberate:

- **adaptive behaviour** is required;
- **adaptive software in the field** is not.

A deployed node may react continuously to bearer availability, evidence, policy validity, environmental state, trust state and local failures. It may not invent new authority, new trust roots, new protocol semantics or new bearer permissions because an online learner decided they looked useful.

## 2. Two lifecycle domains

### 2.1 Peacetime evolution plane

Outside the deployed runtime, engineering systems may consume:

- decision, execution and effect receipts;
- real incident traces;
- simulator results;
- false refusals;
- unstable switching traces;
- stale-evidence events;
- sensor disagreements;
- dataplane mismatches;
- authority outages;
- restart and recovery failures; and
- adversarial or fault-injection scenarios.

These inputs may be used to propose changes to policy, thresholds, scheduling, evidence handling, adapters, code or test cases.

The improvement plane MAY use REMORA, LLMs, search, optimisation, formal methods, simulation or other engineering tools. Those tools are development dependencies, not SURVIVAL runtime dependencies.

### 2.2 SURVIVAL runtime

A promoted release executes a fixed implementation with a bounded authority envelope.

The runtime MUST NOT require:

- an LLM;
- cloud inference;
- online code generation;
- a central decision service;
- interactive operator approval for ordinary bearer repair; or
- uncontrolled self-deployment.

## 3. Improvement is not deployment

A candidate improvement MUST NOT reach the field merely because it performed better on one trace or was generated by a trusted engineering tool.

The target promotion pipeline is:

```text
OBSERVE
  ↓
REPLAY
  ↓
PROPOSE CANDIDATE
  ↓
SIMULATE
  ↓
FALSIFY
  ↓
PROPERTY TEST
  ↓
CONFORMANCE TEST
  ↓
SECURITY / FAULT INJECTION
  ↓
COMPARE AGAINST BASELINES
  ↓
SIGNED PROMOTION
  ↓
SURVIVAL RELEASE N+1
```

A regression in a safety invariant blocks promotion even when aggregate performance improves.

## 4. Release boundary

A promoted SURVIVAL release should eventually be represented by a signed release manifest binding at least:

```text
software artifact hash
protocol version
policy schema version
trust roots / trust profile
conformance suite version
configuration schema
supported evidence profiles
supported dataplane profiles
```

The purpose is to make the operational base attributable and reproducible.

The world state remains mutable. The execution base does not silently mutate with it.

## 5. Promotion principles

A candidate release should be promoted only if evidence demonstrates that it either:

1. preserves all mandatory safety invariants while improving a declared performance or resilience metric; or
2. closes a demonstrated correctness or security gap without introducing an unacceptable regression elsewhere.

Pilotfish MUST record negative results rather than hiding cases where a candidate loses to a simpler baseline.

## 6. Counterfactual improvement

The most useful peacetime loop is counterfactual replay:

```text
real trace
   │
   ├── release N actual decision
   │
   └── candidate N+1 counterfactual decision
                 │
                 ▼
        compare safety, refusal,
        stability and recovery
```

The candidate should be evaluated against an oracle or independently defined requirements where possible, not merely against the previous Pilotfish implementation.

## 7. Runtime self-healing remains fully autonomous

Freezing the execution base does not make the deployed system passive.

SURVIVAL may autonomously:

- remove a failed or newly ineligible bearer;
- choose another bearer already inside the authority envelope;
- expire stale evidence;
- retry a failed dataplane operation;
- reconcile desired and observed state;
- recover after process restart;
- restore receipt continuity;
- continue while central authority is unreachable; and
- reduce its permitted action set as confidence falls.

This is runtime adaptation within a proven envelope, not online software evolution.

## 8. Research objective

The V2 research question is not whether Pilotfish can make more complicated decisions than existing systems.

It is whether a system can combine:

- deterministic autonomous operation;
- policy-bounded self-healing;
- trustworthy evidence;
- stable bearer selection;
- offline survivability;
- execution/effect verification; and
- controlled improvement between releases

without introducing a central or probabilistic runtime dependency.

That claim must be demonstrated experimentally before it is asserted as superiority.
